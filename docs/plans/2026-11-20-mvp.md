# wakaru MVP 実装プラン

日本語と英語が混ざる会議（ブラウザで開いた Google Meet / Teams など）のタブ音声を、Chrome のオンデバイス音声認識で文字起こしし、話された言語を自動で判定して、もう一方の言語へ訳してサイドパネルに字幕表示する Chrome 拡張。

## 前提（2026-11-20 に手元で検証済み）

検証環境: Chrome Beta 159 / Apple M5 / 32GB。検証は通常の Web ページ（`http://127.0.0.1`）で行った。拡張のサイドパネルの中では未検証で、Task 1 で確かめる。

実際に使うのは安定版の Chrome 157（2026-11-20 時点で 157.0.8103.80）。下の前提は Beta 159 で確かめたものなので、Task 1 で 157 でも確かめ直す。

- 日英2本の `SpeechRecognition`（`processLocally = true`）は、同じ音声トラック（`start(track)` / `track.clone()`）で同時に動く
- 各認識器は他言語の発話にほぼ何も返さない。紛らわしい誤認識を返すのは主に英語側で、`LanguageDetector` で弾ける（正しい英文は `en:1.00`、誤認識は `es` / `de` 等）
- `confidence` はオンデバイスで常に `1` なので使えない
- 日本語側の確定結果（FINAL）は語の間に空白が入る（`来週 の リリース`）。途中経過（interim）には空白が入らない
- 発話の後が完全な無音だと、確定が `stop()` まで遅れたり、来なかったりする
- 確定までの遅延は話し終わりから約 0.7〜1.1 秒
- 翻訳は PLaMo 3 Translate 0.8B（Q4_K_M、wllama + WebGPU）で 1 文あたり 0.2〜0.6 秒。質は Chrome Translator API より明らかに良い。Chrome は 2〜45ms
- `SpeechRecognition.install()` と `Translator.create()` は、モデルが `downloadable` の状態だとユーザー操作（クリック等）の中でないと失敗する
- wllama の呼び出し形は tanakh/plamo-translate-desktop `3d69a11` の `extension/engine.js` と、テストページで動いた次の形で確定している: `new Wllama({ default: wasmUrl }, { logger })`、`loadModel([file], { n_ctx, n_gpu_layers, cache_ram_mib })`、`createCompletion({ prompt, max_tokens, temperature, stop, abortSignal, stream?, onData? })`。戻り値は `choices[0].text` と `timings`

レビューで分かった制約（公式ドキュメントで確認済み）:

- `tabCapture` は「拡張が呼び出された後」にしか使えない。`targetTabId` に指定できるのは activeTab が付与されたタブだけ。activeTab はアクションのクリックなどで付き、サイドパネル内のクリックでは付かない。`setPanelBehavior({ openPanelOnActionClick: true })` でパネルを開いた場合も付かない（Chromium の issue 336592430 で仕様と回答されている）
- キャプチャ中のタブは音が止まる。`AudioContext.destination` に流し直す必要がある
- 言語パックの「導入済み」状態は、オリジンごとに隠される。127.0.0.1 で入れた分は拡張では使えず、拡張のオリジンで改めて `install()` が要る
- npm の wllama（3.8.1）は PLaMo 3 のトークナイザより古いので使えない

## スコープ

MVP に含める:

- 入力は、アイコンを押したタブの音声だけ（`chrome.tabCapture`）
- 言語は ja と en だけ
- 表示はサイドパネル。各発話の原文、言語ラベル、訳文、途中経過の行を出す
- 翻訳エンジンは PLaMo（ブラウザ内）と Chrome Translator API を設定で切り替える。標準は PLaMo
- 設定は `chrome.storage.local` に保存する。字幕と文字起こしは保存しない

MVP に含めない（後で足す）:

- マイク入力（自分の声）。Meet などは自分の声をタブに流さないので、相手の発言を理解するという目的には要らない
- 話者分離、仮訳（Chrome で即訳してから PLaMo に置き換える）、エクスポート、用語集
- 2B 以上のモデル、ローカルサーバー（`llama-server`）を使う翻訳エンジン
- 再生先のスピーカーを Meet の設定に合わせること（下の Task 6 で現象だけ確かめる）

## 構成

```
background.ts : アイコンのクリック → サイドパネルを開き、対象タブの ID を storage.session に置く
サイドパネル (sidepanel/index.html) ── 処理は全部ここで動かす
  ├ TabAudio        : tabCapture → MediaStream → 音を再生し直す → 音声トラック
  ├ DualRecognizer  : ja/en の SpeechRecognition ×2（世代番号つきで再起動、異常な再起動だけを数える）
  ├ StallFinalizer  : 途中経過が止まった発話を確定扱いにする
  ├ Arbiter         : 2 本の確定結果を時間の窓でまとめ、LanguageDetector で採用する側を決める
  ├ TranslationQueue: 発話を 1 件ずつ翻訳する（1 件 5 秒で打ち切り）
  │   └ TranslatorBackend = PlamoBackend (wllama/WebGPU) | ChromeBackend (Translator API)
  └ UI              : 状態に応じたボタン、字幕リスト、途中経過、準備状況、デバッグ表示
```

サイドパネルにまとめる理由（Why not offscreen document）:

- `install()` と `Translator.create()` にはユーザー操作が要る。操作できるのはサイドパネルだけ
- offscreen document で `SpeechRecognition` が動くかは確かめていない
- サイドパネルを閉じたら翻訳が止まる。この動作は MVP では許容する

入口を `action.onClicked` にする理由（Why not `setPanelBehavior({ openPanelOnActionClick: true })`）: そちらでは activeTab が付かず、`tabCapture` が使えない。`action.onClicked` ならクリックしたタブに activeTab が付き、パネルから `getMediaStreamId({ targetTabId })` を呼べる見込み。この見込みは Task 1 で確かめる。代わりにアイコンでパネルを閉じられなくなるので、パネル内に閉じるボタン（`window.close()`）を置く。

## 状態遷移

```
idle ─(準備)→ preparing ─→ ready ─(開始)→ running ─(停止 / タブ終了)→ stopping ─→ ready
                                                     どの状態からも → error ─(リセット)→ idle
```

| 状態 | 押せるボタン |
|---|---|
| idle | 言語パックを準備、翻訳モデルを準備、エンジン選択、閉じる |
| preparing | 閉じる（ダウンロード中は「閉じると中断されます」と表示） |
| ready | 開始、エンジン選択、クリア、閉じる |
| running | 停止、クリア、閉じる（エンジン選択は無効。翻訳中の件と `dispose()` の競合を避けるため） |
| error | リセット、閉じる |

`ready` に入れる条件: 言語パック（ja-JP、en-US）、LanguageDetector、選択中のエンジンがすべて使える状態。

停止の手順:

1. 両方の認識器を `abort()` する
2. `arbiter.flushAll()` で残りを判定する
3. キューに残っている翻訳を待つ（最大 5 秒）
4. 元のトラックとクローンをすべて `stop()` する
5. `AudioContext` を `close()` する

### Task 2: 純粋ロジック（テスト先行）

`dev/utterances.json` は次の形で、テストとテスト音声の両方から読む。

```json
[{ "lang": "ja", "text": "来週のリリースについて、スケジュールを確認させてください。" }, ...]
```

`src/asr/normalize.ts`

- `normalizeJa(text)`: 前後どちらかが CJK 文字の空白を消す。`来週 の リリース` → `来週のリリース`、`Slack に 共有` → `Slackに共有`。英字同士の間の空白は残す（`API rate`）

`src/mt/tokens.ts`

- `estimateTokens(text)`: tanakh の推定関数を移植する（CJK は 1 文字 1 トークン、それ以外は 4 文字 1 トークン）

`src/asr/arbiter.ts`

```ts
type Lang = 'ja' | 'en';
type Final = { lang: Lang; text: string; at: number; synthetic: boolean }; // at: performance.now()
// lang が null は「どちらも有効でなく捨てた発話」。text は空で、確定結果はすべて rejected に入る
type Decision = { lang: Lang | null; text: string; firstAt: number; decidedAt: number; rejected: Final[] };
type LangDetect = (text: string) => Promise<{ lang: string; confidence: number }>;

class Arbiter {
  constructor(opts: { windowMs: number; enMinConfidence: number; enShortMinConfidence: number;
                      detect: LangDetect; now: () => number });
  push(f: Final): void;
  flushDue(): Promise<Decision[]>;   // 窓が閉じた分を判定する。100ms ごとに呼ぶ
  flushAll(): Promise<Decision[]>;   // 停止時に残りを全部判定する
}
```

窓の扱い:

- 最初の確定結果が来た時刻（`firstAt`）から `windowMs` の間に来たものを、1 つの発話候補にまとめる
- 窓の中に ja と en の両方がそろったら、`windowMs` を待たずにその時点で窓を閉じる
- 同じ言語の確定が窓の中に 2 つ来たら、連結する（ja は空白なし、en は空白区切り）
- 直前に採用した発話の窓が閉じた時刻から `windowMs` 以内に来た、反対の言語の候補は捨てる（`rejected` に残す）。`Okay` と `OK` のような短い語の二重表示を防ぐため
  - 起点を `decidedAt` にしない。`decidedAt` には `detect` にかかった時間が入るので、判定が遅いと、その間に来た反対の言語の本物の返事まで捨ててしまう
- `detect` は非同期なので、`flushDue()` が重なって呼ばれても、判定は窓を閉じた順に直列で行う
- 遅延の計測の起点は `firstAt` とする

判定ルール:

- 英語の候補は、`detect` の判定が `en` で、確からしさが閾値以上のときだけ有効にする。閾値は通常 `enMinConfidence`。日本語側が空で英語側が 3 語以下のときだけ `enShortMinConfidence` を使う（"Yeah" や "Sure" を拾うため）
- 日本語の候補は、空でなければ有効
- 有効な候補が 1 つならそれを採用する。2 つあれば、空白を除いた文字数が多い方を採用し、同じなら ja を採用する
  - 日本語と英語の文字数は本来比べられない量。両方が有効になるのは短い語と英語側の誤認識だけ、という実測を前提にした規則なので、Task 6 で外れた例を集める
- 有効な候補がなければ、その発話は捨てる（`rejected` に残す）
- かぶせて話す場面（Task 3.5）: 両方の言語が中身のある発話なら、2 発話として両方採用し、それぞれの最初の確定が届いた順（話し終わった順に近い）に並べる。中身のある発話には、直前の判定から窓以内の反対言語を捨てる規則も適用しない
  - 日本語の中身: 平仮名・漢字が 4 文字以上。言語違いの認識器が日本語側に出すゴミは英字（`OK`、`No`、`EX`）。片仮名は数えない（日本語の認識器が英語を片仮名で書くと、英語と二重に出るため）
  - 英語の中身: `detect` が `en` で確信度 `enMinConfidence` 以上、かつ 4 語以上。英語側のゴミは `es` / `de` 判定か、`Ok Google`・`Disney` のような短い語
  - 短い返事（「はい」など）が長い発話と重なると、今までどおり片方だけになる

テストケース（`detect` はスタブ。値は Chrome の LanguageDetector で実測したもの。2026-11-20 に Beta 159 で測り、`Yeah` と `Okay` は Task 1 で 157 で測った値に差し替えた）:

| ja の確定 | en の確定（detect の結果） | 期待 |
|---|---|---|
| `来週のリリースについてスケジュールを確認させてください` | `Schedu schedule`（de 0.81） | ja を採用、en を捨てる |
| 同上 | `Ok Google`（en 0.94） | ja を採用（文字数が多い） |
| なし | `Sure we are planning to ship the new feature on Wednesday`（en 1.00） | en を採用 |

| `はい` | なし | ja を採用 |

| `来週` と `のリリース`（同じ窓） | なし | ja の `来週のリリース` を採用（連結） |

`src/asr/stallFinalizer.ts`

- 時刻は外から渡す: `update(lang, generation, interimText, now)`、`onRealFinal(lang, generation, text, now): boolean`、`tick(now): Final[]`
- 途中経過が `stallMs` の間変わらなければ、`synthetic: true` の確定結果を出す
- 確定扱いにしても認識器は再起動しない。Task 3 の実機では、再起動が発話の切れ目に来て、次の発話の頭（`Sure`、`Most`）が欠けた。新しい認識器を先に起動してから古い方を止める形も採らない（新しい認識器は起動するまで音を聞いていないので、頭が欠けるのは同じ）。動かし続けた認識器は、次の発話で止まった途中経過を置き換えるか、確定扱いにした文で始まる結果を遅れて出す。確定扱いにした文で始まる途中経過と確定は、その先頭を取り除き、残りを新しい途中経過として扱う（残りが空なら捨てる）。先頭ごと捨てると、「はい」の後の「はいそうです」が丸ごと消えるため。比べ方は、ja は空白を除いた文字、en は単語単位（`Yo` で止まった後の `You know` を続きとみなさないため）
  - 遅れて来た確定の残りは別の行になる（`No worries I said the API rate limit` と `is causing the timeout errors`）。分かれるが、落ちも二重にもならない
- 確定扱いにするのは、もう一方の言語の途中経過も `stallMs` の間変わっていないとき（無音のとき）だけにする。また、自分が止まった後にもう一方の言語が聞こえていた途中経過は、確定扱いにせず捨てる。Task 3 の実機では、言語違いの側の認識器が発話の頭の 1〜2 語（「No worries…」の間の日本語側の `No` など）を出したまま更新を止め、それが確定扱いになって二重表示が 3 件出た。そのとき StallFinalizer が出した 9 件はすべてこの種類だった
  - 代わりに、確定が来ないまま相手に話をかぶせられた本物の短い返事も捨てる。かぶりは Task 3.5 で測る
- 確定扱いの結果の `at` は、途中経過が最後に変わった時刻にする。`tick` の時刻にすると `stallMs` だけ遅れ、もう一方の認識器の確定と同じ窓に入らない（`windowMs` 800 < `stallMs` 1200）。遅延の計測にも待ち時間が入ってしまう
- 本物の確定が来たら、その言語の途中経過をクリアする（同じ文が後で確定扱いになって二重に出るのを防ぐ）。`onRealFinal(lang, generation, text)` が false を返したら、呼び出し側はその確定を重複として捨てる
- 確定扱いの結果は、本物と同じ経路（normalize → Arbiter）に流す

### Task 4: 翻訳エンジン

`src/mt/backend.ts`

```ts
export interface TranslatorBackend {
  readonly id: 'plamo' | 'chrome';
  prepare(onProgress?: (p: { phase: 'download' | 'load'; ratio?: number }) => void): Promise<void>;
  translate(text: string, from: Lang, to: Lang, signal: AbortSignal): Promise<string>;
  clearContext(): void;    // 「クリア」ボタンから呼ぶ。Chrome 側は何もしない
  dispose(): Promise<void>;
}
```

- `chrome.ts`: `Translator.create()` を ja→en と en→ja で 1 つずつ作り、使い回す
- `plamo/modelStore.ts`: tanakh の engine.js の `download()` / `removeStaleParts()` を移植する
  - 対象は `pfnet/plamo-3-translate-0.8b-GGUF` の `plamo-3-translate-0.8b-Q4_K_M.gguf`（revision `e10c327b7a7ce84ffc427cb4b09360b781429fda`、573,126,848 bytes）
  - `.part` に書き、64MB ごとに書き込みストリームを `close()` して `createWritable({ keepExistingData: true })` で開き直す。OPFS は close したときにしか中身を残さないので、パネルを閉じても次回は `Range` で続きから取れる
  - 起動時に残った `.part` 以外の `.crswap` などを掃除する
  - 完全性はサイズで確認する。SHA-256 は確認しない（Why not: WebCrypto に逐次計算の API がなく、573MB をメモリに載せる必要がある。revision を固定した HTTPS の URL から取るので、改ざんのリスクは低い）
- `plamo/backend.ts`: tanakh の engine.js の `load()` / `complete()` / `isCrash()` / `crashed()` を移植する
  - 読み込みは `loadModel([file], { n_ctx: 4096, n_gpu_layers: 999, cache_ram_mib: 0 })`。WebGPU が使えないときは `n_gpu_layers: 0`（CPU）で読み込み、準備状況に「CPU（遅い）」と出す
  - 翻訳は `createCompletion({ prompt, max_tokens: min(512, estimateTokens(text) * 3 + 64), temperature: 0, stop: ['<|plamo:tag|>'], abortSignal })`。MVP では訳文を逐次表示しないので、`stream` は使わない
  - wllama がクラッシュしたら（メモリ不足、GPU デバイスの喪失など）、`dispose()` して OPFS から読み込み直す。読み込み直している間の発話は原文だけ流す
- エンジンが失敗しても、別のエンジンに勝手に切り替えない。エラーを字幕の行に出し、原文だけ表示する（Sakutto と同じ方針。品質の違うエンジンに黙って替わると気づけない）
- エンジンを切り替えたときは、前のエンジンを `dispose()` する（PLaMo の GPU メモリを解放するため）。切り替えは running 以外の状態でだけ許す

完了条件: デバッグ用のボタンで、固定した ja と en の文を両エンジンで訳せ、所要時間がログに出る。エンジンを切り替えた後も動く。`dev/player.html` の 9 発話を PLaMo で通せる。
